01

The order a query actually runs in

Most beginner bugs are one misunderstanding: you write a query top-down, but the database runs it in a different order. WHERE can't see an alias you defined in SELECT, and WHERE can't filter on COUNT(*) — because neither exists yet when WHERE runs.

WRITTEN: SELECT · FROM · JOIN · WHERE · GROUP BY · HAVING · ORDER BY · LIMIT  →  EXECUTED:
  1. 1FROMLoad the base table into memory as a row set.
  2. 2JOIN … ONStitch other tables on; the row count can grow here.
  3. 3WHEREThrow away individual rows. No aggregates exist yet.
  4. 4GROUP BYCollapse surviving rows into buckets.
  5. 5HAVINGThrow away whole buckets. This is where aggregates filter.
  6. 6SELECTCompute the output columns. Aliases are born here.
  7. 7DISTINCTDrop duplicate output rows.
  8. 8ORDER BYSort. Aliases work here — they already exist.
  9. 9LIMIT / OFFSETSlice the sorted result. Always sort before you slice.
Use this

The lab below prints this pipeline with a live row count at every stage. When a query returns the wrong number of rows, read the trace left to right and find the step where the count went wrong.

03

Reading data

Retrieval

select
SELECT id, name, salary FROM employees;
SELECT DISTINCT role FROM employees;
SELECT name AS employee, salary / 12 AS monthly_pay FROM employees;

Filtering

where
SELECT * FROM employees WHERE salary > 80000;
SELECT * FROM orders WHERE status = 'shipped' AND amount > 1000;
SELECT * FROM employees WHERE role IN ('Manager', 'Designer');
SELECT * FROM employees WHERE salary BETWEEN 55000 AND 70000;
SELECT * FROM orders WHERE customer LIKE 'North%';
SELECT * FROM orders WHERE order_date >= '2024-04-01';
=  !=  <>

Exact match and its negation. <> is the ANSI spelling; both work nearly everywhere.

IN (…)

Match any value in a list. Cleaner than a chain of ORs, and easier to swap for a subquery later.

BETWEEN a AND b

Inclusive on both ends. For dates, prefer >= start AND < next_day so timestamps don't fall through.

LIKE '%x_'

% is any run of characters, _ is exactly one. A leading % kills index use.

IS NULL

The only way to test for null. = NULL is never true — see section 04.

EXISTS (…)

True if a correlated subquery returns any row. Often faster than IN on large sets.

Sorting and slicing

order by · limit
SELECT name, hire_date FROM employees ORDER BY hire_date DESC;
SELECT name, salary FROM employees ORDER BY salary DESC LIMIT 5;

-- pagination: page 3 at 20 rows a page
SELECT id, customer FROM orders ORDER BY id LIMIT 20 OFFSET 40;
Trap

LIMIT without ORDER BY returns an arbitrary set of rows. It may look stable in testing and change the day the table grows or the plan changes. If order matters, say so — and make the sort key unique, or add a tiebreaker like ORDER BY created_at DESC, id DESC.

04

NULL, the thing that quietly eats rows

NULL means unknown, not zero and not empty string. Comparing anything to unknown gives unknown, and WHERE keeps only rows that are definitely true — so a null silently drops out of both sides of a filter.

null handling
SELECT * FROM employees WHERE dept_id IS NULL;      -- correct
SELECT * FROM employees WHERE dept_id = NULL;       -- always zero rows

-- these two together do NOT cover every row:
SELECT COUNT(*) FROM employees WHERE role = 'Engineer';
SELECT COUNT(*) FROM employees WHERE role != 'Engineer';   -- nulls vanish

-- substitute a fallback value
SELECT name, COALESCE(dept_id, 0) AS dept FROM employees;

-- COUNT(*) counts rows; COUNT(col) skips nulls in that column
SELECT COUNT(*) AS rows_total, COUNT(dept_id) AS with_dept FROM employees;

-- NULLIF: turn a sentinel back into a null, and dodge divide-by-zero
SELECT total / NULLIF(order_count, 0) AS avg_order FROM summary;
Interview answer

"Why does COUNT(*) differ from COUNT(column)?" — COUNT(*) counts rows, COUNT(column) counts non-null values in that column. Run both in the lab against employees.dept_id: 12 versus 11.

05

Joins

A join answers "which rows in B belong with this row in A?" The join type only decides what happens to rows with no match.

INNER JOIN

Only rows that matched on both sides. Unmatched rows disappear from the result entirely.

LEFT JOIN

Every row from the left table; right-side columns come back NULL where nothing matched.

RIGHT JOIN

The mirror image. Rare in practice — most people flip the table order and use LEFT for readability.

FULL OUTER JOIN

Everything from both sides, nulls where either is missing. Useful for reconciling two systems.

CROSS JOIN

Every combination of both tables. Deliberate for calendars and grids; a bug when it's an accident.

SELF JOIN

Join a table to itself with two aliases — employees to their managers, rows to their predecessors.

joins
-- inner: only employees who have a department
SELECT e.name, d.name AS department
FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;

-- left: every employee, department null when unassigned
SELECT e.name, d.name AS department
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id;

-- anti-join: rows on the left with NO match on the right
SELECT d.name
FROM departments d
LEFT JOIN employees e ON d.id = e.dept_id
WHERE e.id IS NULL;

-- self join: everyone next to their manager
SELECT staff.name AS employee, boss.name AS manager
FROM employees staff
LEFT JOIN employees boss ON staff.manager_id = boss.id;

-- three tables
SELECT o.id, e.name AS rep, d.name AS department
FROM orders o
JOIN employees e ON o.employee_id = e.id
JOIN departments d ON e.dept_id = d.id;
Trap

Putting a right-table condition in WHERE turns a LEFT JOIN back into an inner one, because the NULL fails the test. Filter the right table inside ON instead: LEFT JOIN orders o ON e.id = o.employee_id AND o.status = 'shipped'.

Trap

If a join makes your row count jump, you joined a one-to-many relationship and every left row is now duplicated once per match. Sums computed afterwards will be inflated. Aggregate the many-side first, then join the result.

06

Aggregation and grouping

aggregates
SELECT COUNT(*) AS headcount FROM employees;
SELECT AVG(salary) AS avg_salary, MIN(salary), MAX(salary) FROM employees;
SELECT SUM(amount) AS revenue FROM orders WHERE status = 'shipped';
SELECT COUNT(DISTINCT role) AS distinct_roles FROM employees;
group by · having
-- one output row per group
SELECT role, COUNT(*) AS people, AVG(salary) AS avg_pay
FROM employees
GROUP BY role
ORDER BY people DESC;

-- WHERE filters rows BEFORE grouping, HAVING filters groups AFTER
SELECT e.name, SUM(o.amount) AS revenue
FROM employees e
JOIN orders o ON e.id = o.employee_id
WHERE o.status = 'shipped'
GROUP BY e.name
HAVING SUM(o.amount) > 2000
ORDER BY revenue DESC;
Rule

Every non-aggregated column in SELECT must appear in GROUP BY. Postgres and SQL Server enforce it; MySQL and SQLite may silently pick an arbitrary row instead, which is how a report gets quietly wrong. The lab enforces the strict rule.

Date and string work you'll use constantly

scalar functions
SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM contacts;
SELECT UPPER(email), TRIM(name), LENGTH(name), SUBSTRING(phone, 1, 3) FROM contacts;
SELECT ROUND(AVG(salary), 2) AS avg_salary FROM employees;

-- monthly rollup (Postgres)
SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount)
FROM orders GROUP BY 1 ORDER BY 1;

-- monthly rollup (MySQL)
SELECT DATE_FORMAT(order_date, '%Y-%m') AS month, SUM(amount)
FROM orders GROUP BY month ORDER BY month;
07

CTEs, windows, CASE

CTEs — name your steps

A common table expression is a named result you build on. Prefer it to nested subqueries: each step gets a name, and you can run the pieces separately while debugging.

with
WITH shipped AS (
  SELECT employee_id, SUM(amount) AS revenue
  FROM orders
  WHERE status = 'shipped'
  GROUP BY employee_id
)
SELECT e.name, s.revenue
FROM employees e
JOIN shipped s ON e.id = s.employee_id
ORDER BY s.revenue DESC;

Window functions — aggregate without collapsing rows

A GROUP BY gives you one row per group. A window gives every row its group's answer alongside it — ranks, running totals, previous-row comparisons.

over()
-- rank within each department
SELECT name, salary, dept_id,
       RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rank_in_dept,
       ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS n
FROM employees;

-- each row next to its department average
SELECT name, salary,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
FROM employees;

-- running total and month-over-month change
SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date) AS running_total,
       amount - LAG(amount) OVER (ORDER BY order_date) AS change_vs_prev
FROM orders;

RANK leaves gaps after ties (1, 1, 3), DENSE_RANK doesn't (1, 1, 2), ROW_NUMBER never ties. Pick deliberately — "top 3 earners" with ties is a different question depending on which you use.

CASE — conditional logic inline

case
SELECT name, salary,
  CASE WHEN salary < 60000 THEN 'band 1'
       WHEN salary < 90000 THEN 'band 2'
       ELSE 'band 3'
  END AS pay_band
FROM employees;

-- pivot: statuses become columns
SELECT customer,
  SUM(CASE WHEN status = 'shipped' THEN amount ELSE 0 END) AS shipped,
  SUM(CASE WHEN status = 'pending' THEN amount ELSE 0 END) AS pending
FROM orders
GROUP BY customer;

Set operations

union · except · intersect
SELECT name FROM employees_2023
UNION      -- de-duplicates; UNION ALL keeps duplicates and is faster
SELECT name FROM employees_2024;

SELECT id FROM orders EXCEPT SELECT order_id FROM invoices;   -- unbilled
SELECT id FROM orders INTERSECT SELECT order_id FROM invoices; -- both
08

Writing data safely

insert · update · delete
INSERT INTO employees (name, dept_id, role, salary)
VALUES ('Nadia Cole', 1, 'Engineer', 92000);

INSERT INTO employees (name, role) VALUES
  ('Omar Diaz', 'Analyst'),
  ('Priya Raman', 'Designer');

UPDATE employees SET salary = salary * 1.04 WHERE dept_id = 1;

DELETE FROM orders WHERE status = 'cancelled' AND order_date < '2024-01-01';
The one that ends careers

An UPDATE or DELETE without WHERE hits every row in the table. Write the WHERE clause first, run it as a SELECT, confirm the row count, and only then change the verb.

The safe write ritual

transaction
-- 1. see exactly what you're about to touch
SELECT * FROM employees WHERE dept_id = 3;

-- 2. wrap the change so you can take it back
BEGIN;
  UPDATE employees SET dept_id = 1 WHERE dept_id = 3;
  -- 3. verify inside the transaction
  SELECT COUNT(*) FROM employees WHERE dept_id = 1;
-- 4. keep it, or undo it
COMMIT;   -- or: ROLLBACK;

Upsert

insert … on conflict
-- Postgres / SQLite
INSERT INTO inventory (sku, qty) VALUES ('A-100', 5)
ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty;

-- MySQL
INSERT INTO inventory (sku, qty) VALUES ('A-100', 5)
ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty);
Habits that keep you employed

Never run a write against production that you haven't run as a SELECT first. Know whether your client has autocommit on. Prefer a soft delete (deleted_at timestamp) when the data has any chance of being wanted back.

10

Performance you can speak to

Nobody expects a junior to tune a query planner. They do expect you to know why a query is slow and to read a plan without panicking.

Index = sorted lookup

An index is a sorted copy of one or more columns with pointers back to the rows. It makes finding rows fast and makes writes slightly slower.

Index the join and filter keys

Foreign keys, columns in WHERE, and sort keys. Primary keys are already indexed.

Functions kill indexes

WHERE YEAR(order_date) = 2024 can't use the index. Use order_date >= '2024-01-01' AND order_date < '2025-01-01'.

Leading wildcards too

LIKE '%son' forces a full scan. LIKE 'john%' can use an index.

Read the plan

EXPLAIN ANALYZE <query>. "Seq Scan" on a big table with a selective filter is the usual smoking gun.

Select fewer columns

SELECT * drags every column over the wire and blocks index-only scans. Name what you need.

Say this out loud

"It's scanning the whole table because the filter is wrapped in a function, so the index on that column can't be used." That sentence, said about a real query, is most of what a junior data role wants to hear.

11

Recipes for the questions you'll be asked

Top N per group

recipe
WITH ranked AS (
  SELECT name, dept_id, salary,
         ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS n
  FROM employees
)
SELECT name, dept_id, salary FROM ranked WHERE n <= 2;

Find duplicates

recipe
SELECT email, COUNT(*) AS copies
FROM customers
GROUP BY email
HAVING COUNT(*) > 1
ORDER BY copies DESC;

Rows with no match (customers who never ordered)

recipe
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.id IS NULL;

Dormant for 90 days

recipe
SELECT c.id, c.name, MAX(o.order_date) AS last_order
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
GROUP BY c.id, c.name
HAVING MAX(o.order_date) < CURRENT_DATE - INTERVAL '90 days'
    OR MAX(o.order_date) IS NULL;

Month over month

recipe
WITH monthly AS (
  SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS revenue
  FROM orders GROUP BY 1
)
SELECT month, revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS delta,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1) AS pct_change
FROM monthly ORDER BY month;

Percent of total

recipe
SELECT status,
       SUM(amount) AS revenue,
       ROUND(100.0 * SUM(amount) / SUM(SUM(amount)) OVER (), 1) AS pct_of_total
FROM orders GROUP BY status ORDER BY revenue DESC;
12

Anti-patterns reviewers flag

Implicit comma joins

FROM a, b WHERE a.id = b.a_id works but hides the join condition. Use explicit JOIN … ON.

SELECT * in code

Fine while exploring, fragile in anything that ships — column order and count change under you.

String-built SQL

Concatenating user input is how injection happens. Use parameters: WHERE id = ?.

DISTINCT as a bandage

Sprinkling DISTINCT to fix duplicate rows hides a wrong join. Fix the join grain instead.

Aliases like a, b, x1

Alias for meaning — emp, ord, dept. You'll read the query more often than you wrote it.

OR across columns

WHERE a = 1 OR b = 2 often defeats indexes. A UNION ALL of two indexed queries can be far faster.

Floats for money

Use NUMERIC/DECIMAL. Floating point rounding turns into cent-level discrepancies in reports.

No formatting

One keyword per line, indented joins, uppercase keywords. Reviewers judge readability before logic.
