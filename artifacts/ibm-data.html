01 / SHAPES OF DATA

Structure is what decides everything downstream

Before you can store, query, or model anything, you have to know how much shape the data arrived with. Structure determines which store it belongs in, which tools can read it, and how much work stands between raw input and an answer. IBM frames enterprise data along this spectrum, and the four V's describe the pressure it puts on any system that has to hold it.

Structured

Fits a schema already

Fixed fields with declared types and lengths — relational tables, mainframe VSAM files, COBOL copybook records, CSV extracts. Every value has a known position and meaning before you read it.

Cheap to query, expensive to change. Altering a schema means migrating everything already written to it.

Db2VSAMSQL~20% of enterprise data
Semi-structured

Carries its own labels

JSON, XML, Avro, Parquet, log lines. There is no separate schema to look up — the tags travel with the values, so two records in the same file can legitimately differ in shape.

This is the native format of APIs and event streams, which is why it dominates anything real-time.

JSONParquetSchema-on-read
Unstructured

Meaning has to be extracted

Contracts, emails, call recordings, images, scanned claims, support tickets. The information is real but nothing about the storage format exposes it.

The dominant share of what an enterprise holds, and the reason NLP, OCR, and now foundation models moved from research to infrastructure.

The four V's

What makes data "big"

Volume — how much there is. Velocity — how fast it arrives and how fast it goes stale. Variety — how many shapes and sources it comes in. Veracity — how much of it you can actually trust.

Veracity is the one that gets skipped and the one that sinks projects: a pipeline that moves untrustworthy data faster just produces wrong answers sooner. Many teams add a fifth V, value, as the test of whether the other four were worth paying for.

Metadata

Data about the data

Technical — types, lengths, keys, null rules, partitions. Business — what the field means in plain language and who owns it. Operational — when it last loaded, how many rows, which job wrote it.

Metadata is what makes a data estate searchable instead of merely large. Without it, an analyst cannot tell whether CUST_STAT means account status, statistical segment, or state code.

02 / ONE RECORD, THREE FORMS

The same 54 bytes, read three ways

A COBOL copybook, a relational column, and a JSON key are not three different things — they are three descriptions of the same bytes on a disk. This is the single most useful mental model in enterprise data, because it explains why a modernization project is mostly translation work. Select a field to decode it.

Why fixed width

If every record is exactly 54 bytes, record number 4,000,000 starts at byte 216,000,000. No index lookup, no parsing — arithmetic. That is why batch systems processing millions of records overnight still use it.

Why packed decimal

COMP-3 stores two digits per byte with the sign in the final nibble, and arithmetic stays exact. Binary floating point cannot represent 0.10 exactly; for money, that rounding error is a defect, not a nuance.

Why encoding matters

Mainframes store text in EBCDIC, distributed systems in ASCII or UTF-8. The letter A is 0xC1 in one and 0x41 in the other. Skip the conversion in a pipeline and you get silent corruption, not an error.

03 / WHERE DATA LIVES

Every store is a bet about how the data will be read

There is no general-purpose data store. Each one trades write speed against read speed, or schema rigor against flexibility, and the right choice depends entirely on whether the workload is running the business or analyzing it.

Modeling

Normalized vs. dimensional

Operational systems normalize — each fact stored once, so an update touches one row and cannot contradict itself. Warehouses denormalize into star schemas — a central fact table surrounded by dimension tables — so a report joins two tables instead of eleven.

Both are correct. They optimize for opposite workloads, which is why the same company runs both.

Movement

ETL vs. ELT

ETL transforms before loading: the warehouse only ever receives conforming data, but every new question may require reworking the pipeline. ELT loads raw and transforms in place, which suits cheap elastic storage and exploratory work.

ELT did not replace ETL. Regulated reporting still wants transformation governed and auditable before the data lands.

04 / THE AI LADDER

Four rungs, and you cannot skip one

IBM's organizing framework for getting from raw data to AI in production. The point of the metaphor is strictly ordered: organizations that jump to the top rung end up with impressive models trained on data nobody can vouch for. The ladder is climbed, not leapt.

1
Make data simple and accessible

Collect

Bring data in from wherever it already lives — mainframe files, operational databases, SaaS APIs, sensors, documents — without first demanding that every source be rebuilt. Virtualization matters here: the cheapest way to collect data is often to query it where it sits rather than copy it.

2
Create a business-ready foundation

Organize

Catalog it, define what each field means, trace its lineage, enforce quality rules, mask what is sensitive. This is the rung that gets underfunded because it produces no demo — and the rung whose absence makes every later result contestable.

3
Build and scale with trust

Analyze

Descriptive reporting, statistical analysis, machine learning, model training and validation. Trust is the operative word: a model whose behavior cannot be explained to a regulator or a customer is not deployable in a bank, regardless of accuracy.

4
Operationalize across the business

Infuse

Put the result inside the workflow where the decision actually happens — the claims screen, the credit check, the maintenance schedule. An insight that requires someone to open a dashboard and interpret it has not been infused; it has been filed.

Modernize is the rail alongside the ladder. IBM adds it as the condition that makes the climb possible: hybrid cloud architecture, containerized workloads, and API access to legacy systems. You do not need to replace the mainframe to use its data — but you do need to be able to reach it.
05 / THE METHOD

The Foundational Methodology for Data Science

IBM's ten-stage method, formalized by John Rollins, is a descendant of CRISP-DM with two deliberate differences: it starts from a business question rather than a dataset, and it does not end. Each stage asks one question and produces one artifact. Select a stage to open it.

The two loops are the whole point. Data understanding sends you back to collection when what you gathered cannot answer the question. Evaluation sends you back to modeling when performance falls short. And feedback returns you to business understanding, because a deployed model changes the behavior it was trained to predict — which is why models drift and monitoring is a permanent job, not a launch task.
06 / METHOD VS. SCIENCE

The same discipline, a different deliverable

The data science method is the scientific method with a stakeholder attached. Both insist on a falsifiable claim, controlled evidence, and honest evaluation. They part company at the end: a paper concludes, a model gets deployed and then has to keep being right.

Scientific methodData science methodWhat changes
ObservationBusiness understandingThe phenomenon is chosen by a stakeholder with a cost attached, not by curiosity alone
QuestionAnalytic approachYou also decide the answer's shape — a yes/no, a number, a ranking, a cluster
Background researchData requirementsPrior work tells you which evidence exists; here it tells you which evidence you are allowed to use
HypothesisModelingThe model is the hypothesis — a formal, testable claim about the relationship
ExperimentData collection, understanding, preparationRarely a controlled trial; usually observational data that must be cleaned into fitness
AnalysisEvaluationHeld-out test data replaces the control group as the guard against fooling yourself
ConclusionDeployment + feedbackNo terminal state. The finding enters production and is re-tested continuously
The failure mode both share. In science it is p-hacking; in data science it is leakage and overfitting. Both are the same sin — testing on the evidence you used to build the claim. Holding out data you have not looked at is the discipline that keeps a model honest, exactly as pre-registration does for a study.
07 / QUALITY

Six dimensions, each a test you can actually run

"Good data" is not a judgment call. Quality decomposes into six measurable properties, and each one has a query that either passes or fails. Profiling a dataset means running all six before anyone models anything.

Accuracyvs. reality

Does the value match the real-world thing it describes?

Fails as: a valid ZIP code for the wrong address
Completenessnull rate

Are the required values present at the required grain?

Fails as: 12% of rows missing an income field
Consistencycross-system

Does the same entity agree across every system that holds it?

Fails as: two addresses for one customer
Timelinesslatency

Is it current enough for the decision it will inform?

Fails as: yesterday's balance on a fraud check
Validityvs. rules

Does it conform to its declared format, type, and range?

Fails as: a hire date of 1899-12-31
Uniquenessdup rate

Is each real entity represented exactly once?

Fails as: the same customer under three IDs
Preparation is most of the job. Practitioner surveys have put data collection and preparation at roughly seventy to eighty percent of project effort for years. That number is not a sign of inefficiency — resolving duplicates, reconciling encodings, and deciding what a null means is the analysis, done early.
08 / GOVERNANCE

Who may use which data, for what, and can you prove it

Governance is often mistaken for a compliance tax. It is closer to version control: a set of guarantees that make data safe to reuse by people who did not create it. Without it, every analysis starts by re-establishing trust from scratch.

Catalog

Findability

A searchable inventory of assets with business definitions, owners, and quality scores attached. The question it answers is "does this already exist, and can I trust it?" — the two questions that otherwise get answered by building a duplicate.

Lineage

Traceability

The end-to-end path from source system through every transformation to the number on the report. Required for audits, and the only practical way to answer "which downstream reports break if I change this column?"

Master data

One version of an entity

MDM resolves the same customer, product, or vendor across systems into a single golden record with a stable identifier. This is what makes "how many customers do we have" a question with one answer.

Privacy

Protection and obligation

Classifying PII and PHI, then enforcing masking, encryption, retention limits, and access rules against it — under GDPR, CCPA, HIPAA, and sector regulators. Consent and the right to erasure are data engineering problems long before they are legal ones.

Stewardship

Named accountability

Every critical data element has an owner who decides its definition and an accountable steward who maintains it. Governance without names is a policy document nobody enforces.

AI governance

Models are assets too

The same disciplines now extend to models: documented training data, bias and drift monitoring, explainability for contested decisions, and an approval trail. This is the substance behind watsonx.governance and the EU AI Act alike.

10 / GLOSSARY

Terms worth being precise about

These are the ones that get used loosely and cause real confusion when they do.

Schema-on-write
Structure enforced at load time. Nothing invalid enters the store; changing the structure is expensive.
Schema-on-read
Structure applied when queried. Loading is cheap and flexible; the interpretation burden moves to whoever reads it.
Grain
What one row represents — one order, one order line, one order per day. Mixing grains in a table is the most common modeling error.
Cardinality
How many distinct values a column holds. Drives index choice, join cost, and whether a field is a useful dimension.
Idempotence
Running a pipeline twice produces the same result as running it once. The property that makes a failed job safe to re-run.
Slowly changing dimension
How a warehouse records that an attribute changed — overwrite the old value, or keep both with effective dates.
Data lineage
The traced path from origin through every transformation to final use.
Golden record
The single reconciled version of an entity that MDM produces from conflicting sources.
Feature
An input variable to a model, usually engineered from raw fields rather than used as-is.
Leakage
Information in the training data that would not exist at prediction time. Produces excellent test scores and useless models.
Drift
The world changing until a deployed model's assumptions no longer hold. Detected by monitoring, fixed by retraining.
Copybook
A shared COBOL file defining a record layout. The mainframe's schema definition, reused across every program that reads the file.
EBCDIC
IBM's mainframe character encoding. Incompatible byte-for-byte with ASCII, so every mainframe extract needs conversion.
Packed decimal (COMP-3)
Two digits per byte, sign in the last nibble. Exact base-10 arithmetic for money.
OLTP / OLAP
Transaction processing — many tiny concurrent writes — versus analytical processing — few enormous reads.
Data fabric
An architecture that connects and virtualizes distributed data rather than consolidating it into one store.

The through-line

Every concept here serves one purpose: making a claim about the world that someone else can check. A copybook declares what the bytes mean so a second program reads them the same way. Lineage records where a number came from so an auditor can retrace it. A held-out test set keeps a model from grading its own work. Governance names who is accountable. Data engineering, at its core, is the practice of building systems whose outputs remain verifiable after the people who built them have moved on.
